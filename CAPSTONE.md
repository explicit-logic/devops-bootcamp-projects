# Capstone Project 1: Complete CI/CD Pipeline with EKS and AWS ECR

https://github.com/explicit-logic/eks-module-11.7

A complete CI/CD pipeline that takes a Java app from source code all the way to a running deployment on an EKS cluster in AWS.

Key components built:
- Automatic version incrementing: Implemented an automated process to increment the application's version with each build.
- Automated compilation and packaging: Established a CI/CD pipeline that auto-compiles and packages the Java application.
- Container Image Management: Integrated a mechanism to push application images to a private ECR repository from the Jenkins server and ensure seamless pulling of images by the EKS cluster.
- Deployment to EKS: Automated the deployment of the Java application to the EKS cluster utilizing the 'envsubst' tool for injecting the application image into Kubernetes manifests.
- Version Control Management: Configured the Jenkins pipeline to automatically commit the updated version of the Java application after a successful build.

Key learnings: 
- Set up an Amazon ECR repository and configured Jenkins and the EKS cluster to access it securely.
- Installed and deployed kubeconfig on the Jenkins server so Jenkins could authenticate to the EKS cluster.
- Mapped the Jenkins IAM user into the cluster using 'eksctl create iamidentitymapping' so Jenkins could interact with Kubernetes resources.
- Solved the CI feedback loop by using the 'Ignore Committer Strategy' plugin, which prevents Jenkins from rebuilding when commits are authored by the pipeline’s own email address.
- Configured a multibranch pipeline and set up GitHub credentials to support branch-based builds and repository access.

# Capstone Project 2: Automate Kubernetes Deployment

https://github.com/explicit-logic/ansible-module-15.6

Terraform spins up an EKS cluster on AWS, then an Ansible playbook deploys an Nginx application into a new Kubernetes namespace.

Key components built:
- Terraform: provisions the VPC and an EKS cluster.
- Ansible playbook: uses the kubernetes module to deploy an Nginx app to a dedicated namespace.
- Nginx is exposed via a LoadBalancer Service, so AWS spins up an external load balancer that can be hit in a browser.
- uv manages required Python dependencies needed for the Ansible Kubernetes module.

Key learnings: 
- Ansible authenticates to EKS through a kubeconfig generated by 'aws eks update-kubeconfig' - the region and cluster name have to line up with the Terraform config
- The 'kubernetes.core.k8s' module has hidden dependencies: it won't work unless the Kubernetes Python client, PyYAML, and jsonpatch are installed.
- Collections and core are separate - 'kubernetes.core' has to be added using 'ansible-galaxy'.
- LoadBalancer Service provisions an AWS load balancer that Terraform never tracks, so 'terraform destroy' leaves it orphaned and blocking VPC deletion.

# Capstone Project 3: Complete CI/CD with Terraform

https://github.com/explicit-logic/terraform-module-12.5

A complete CI/CD pipeline for a Java application that builds an artifact, ships a Docker image to Docker Hub, provisions an AWS EC2 instance with Terraform, and deploys the containerized app to it via Docker Compose - all orchestrated by a single Jenkins multibranch pipeline.

Key components built:
- Terraform provisions a VPC, subnet, security group, and an EC2 instance; 'entry-script.sh' (user-data) installs Docker and Docker Compose on the instance at boot.
- A Jenkins multibranch pipeline (Jenkinsfile) runs 4 stages: build the Java app, build and push the Docker image to a private Docker repo, provision the server with Terraform, then deploy.
- The deploy stage reads the instance's public IP from Terraform output, SSHs in, copies server-cmds.sh and docker-compose.yaml, and runs docker compose up to pull and start the private image.

Key learnings: 
- Auto-provision infra from inside a pipeline.
- Installing Terraform into the Jenkins container so the pipeline can run it.
- Storing AWS keys, SSH keys, and Docker creds as Jenkins credentials and injecting them.
- Passing values into Terraform with TF_VAR_ and reading them back with 'terraform output'.

# Capstone Project 4: Deploy MS application in K8s

https://github.com/explicit-logic/kubernetes-module-10.5

Deploys a microservice online shop to a managed Kubernetes cluster on DigitalOcean, then hardens it for production. All the manifests live in one 'config.yaml' applied to its own namespace.

Key components built:
- Kubernetes Deployments and Services for 11 microservices of the online shop.
- A managed Kubernetes cluster was provisioned through the DigitalOcean dashboard with a chosen region, node size, and node count, then accessed locally via a downloaded kubeconfig.
- Readiness and liveness probes were added so Kubernetes can restart unhealthy pods and avoid routing traffic to pods that aren't ready yet.
- CPU and memory requests and limits were set on every container to prevent any single pod from starving others and to help the scheduler place pods intelligently.
- The frontend Service was switched from NodePort to LoadBalancer for a stable cloud-managed external IP, and every Deployment was scaled to 2 replicas for high availability.

Key learnings:
- Provisioning a cluster and connecting with kubectl via kubeconfig.
- Readiness and liveness checks let Kubernetes restart bad pods and route traffic only to ready ones.
- CPU and memory bounds stop any pod from starving others and help the scheduler place them well.
- Replicas give high availability. Setting replicas to 2 keeps the app up even if a pod or node fails.

# Capstone Project 5: Ansible Integration in Jenkins

https://github.com/explicit-logic/ansible-module-15.7

Jenkins connects to a remote Ansible control node, copies the playbook and SSH keys, installs the required Ansible dependencies, and then runs a playbook to configure 2 AWS EC2 managed nodes by installing Docker and docker-compose. It ties together provisioning across DigitalOcean and AWS with a fully automated, end-to-end pipeline.

Key components built:
- A dedicated Ansible control node (DigitalOcean droplet) with Ansible and AWS credentials configured.
- An Ansible playbook that installs Docker and docker-compose on the managed nodes, using architecture detection via 'uname -m'.
- A dynamic AWS inventory using the aws_ec2 plugin, so EC2 IPs are discovered at runtime instead of being hardcoded.
- A Jenkins pipeline with a stage to scp the Ansible files and EC2 key to the control node, and a stage to remotely execute the playbook.
- Configured Jenkins SSH credentials for both the control node and the managed nodes.

Key learnings:
- Ansible's agentless model - only the control node needs Ansible installed; managed nodes are reached over plain SSH.
- Dynamic inventory over static - using the 'aws_ec2' plugin with Boto3 to query AWS for instances at runtime, keyed by tags, so a hardcoded host list is not needed.
- Handling credentials safely in Jenkins - wrapping sh steps in single quotes so the shell expands $PK/$keyFile, keeping secrets out of the interpolated Groovy string.
- SSH key format requirements - Jenkins needs the classic PEM (RSA) format, requiring 'ssh-keygen -m pem' conversion.
- Multi-cloud orchestration - coordinating Jenkins/Ansible on DigitalOcean with managed nodes on AWS in a single workflow.

# Capstone Project 6: Website Monitoring and Recovery

https://github.com/explicit-logic/python-module-14.5

A Python script that monitors a website and automatically recovers it when it goes down. It runs a scheduled HTTP health check against an Nginx container on a DigitalOcean droplet. It responds to failures in two tiers: restarting the Docker container over SSH when the app is down, or rebooting the entire droplet via the DigitalOcean API when the server is unreachable, sending an email alert either way.

Key components built:
- A DigitalOcean droplet running an Nginx Docker container as the monitored target.
- An HTTP health-check using requests that validates the response status code, wrapped in try/except so a totally unreachable site (connection error) is handled separately from a non-200 response.
- An email alerting function (send_notification) that sends notifications through Resend's SMTP.
- A container-restart routine (restart_container) that opens an SSH session with paramiko, finds the stopped nginx container, and starts it again.
- A server-recovery routine (restart_server_and_container) that reboots the droplet via the DigitalOcean API (pydo), polls the reboot action until complete, waits for the droplet to become active, then restarts the container.
- A scheduler using the schedule library to run the full check every 5 minutes in a loop.
- Configuration management via python-dotenv (droplet IP/ID, API token, SMTP credentials, SSH key path) and uv for dependency management.

Key learnings:
- Two-tier failure handling - distinguishing an application failure (site returns non-200, still reachable) from an infrastructure failure (request raises an exception, server unreachable), because each needs a different recovery path.
- If the whole server is down, SSH can't connect either, so recovery has to go through the cloud provider's API rather than the machine itself.
- Programmatic SSH with Paramiko - using SSHClient, AutoAddPolicy, key-based auth, and exec_command to run remote Docker commands from Python.
- Using pydo to reboot a droplet, then polling the action status and droplet state rather than assuming the reboot finished instantly.
- Sending mail over SMTP in Python.
- Pulling the notification logic into a function so both failure tiers can reuse it, and separating detection from reaction.
- Keeping IPs, tokens, and key paths out of the code in environment variables.
